# 向量检索的产品改进：先修稳定性，再减少实际查询工作量

更新：2026-10-27。范围：DuckDB 适配层的 PQ 查询与索引恢复。

10月28日补充：已修复全局跳过重复中心检查与过滤候选固定倍数问题。新回归及347,328次计时SQL补测完成，已测过滤查询严格召回100%，违规ID为0；旧版本部分计划实际丢失WHERE。当前采用先过滤再精确排序，弱过滤仍明显慢，并未证明相对同质量精确SQL稳定提速。完整三组数据、强/弱过滤和64连接对照见[过滤验证报告](../reports/2026-10-27_filtered-vector-search-results.md)。

## 本轮结论

先处理用户会遇到的并发风险和数据库重开后变慢的问题。过夜研究没有得到通过门槛的新算法，不能把参考实现的成绩直接当成产品性能。

已完成并发精排、重复行号恢复两处修复；后续实际 SQL 基准又定位并修复了 PQ 训练不遵守线程上限的问题。100K SIFT、`threads=1` 下，全进程峰值内存由 3.54 GiB 降到 0.53 GiB，构建约从 58 秒增到 63 秒。两种规模合计 7,200 组 top-10 返回 ID 及顺序与改动前一致。完整结果和缺项见 [产品基准报告](../reports/2026-10-27_product-quantization-benchmark.md)。

本次继续实现了可选的 `pq_graph`。此前SIFT 100K、文本10K的较高召回档不能推广到100K文本；原ef256配置在100K文本只有99.45%。最新独立验证将现有搜索宽度固定为1536、精排仍为160条，两个新的1024条代理查询组分别达到99.960938% / 99.951172%，并发时集合保持一致。原登记高预算原图对照全部通过速度门槛，但补入更快的ef768后已有未通过点，不能把原网格通过说成全面达标。默认仍为原向量图，失败原型已撤回；完整新查询、强对照和边界见 [候选补齐报告](../reports/2026-10-27_pq-candidate-rescue-results.md)。此前200条开发查询曲线另见 [100K文本并发报告](../reports/2026-10-27_text-100k-concurrency-results.md)。

| 问题 | 修复前 | 当前改动及验证 |
| --- | --- | --- |
| 多个查询同时首次精排 | 查询共用读锁，却同时修改同一个行号查找表，存在数据竞争 | 首次构建单独加锁；建好后查询仍可并行读取；线程检查和实际多连接 SQL 通过 |
| 重复向量的索引保存与恢复 | 一个图节点保存多个行号，重开时只从节点头恢复一个；索引覆盖校验失败后退回全表扫描 | 为重复节点补存完整行号列表；连续两次重开仍覆盖全部有效行，查询计划保持 `VEXDB_INDEX_SCAN` |
| PQ 训练额外启动大量线程 | SIFT 的 32 个子码本同时训练，即使用户设置 `threads=1`；每个任务持有独立的大型距离下界数组 | 训练分批执行，遵守建索引线程上限，并保留每个子任务原来的随机初始化；原生测试、线程检查、实际 SQL 回归通过 |

另外把 `pq_codes_.empty()` 检查移到索引读锁内，避免与追加编码的写入竞争；构建、替换、加载、删除索引时也使精排查找表失效。

## 这些优化具体如何工作

### 1. 建库内存：限制同时训练的任务数

以128维SIFT的默认PQ配置为例，向量拆成32段，每段各训练一套代表值表。旧路径即使设置threads=1，仍会同时启动32个训练任务；每个任务有独立的“样本数×256”float临时数组，10万样本时约97.7 MiB，32份约3.05 GiB。

现在按用户指定的线程上限分批执行，一批完成再开始下一批，避免大量临时数组同时存活。每个任务仍保留新线程及原来的随机数初态，使已测数据的实际码本、编码和查询结果保持一致。它改变的是执行安排；100K SIFT全进程峰值从3.54降到0.53 GiB，代价是构建约慢8.3%。高维文本的子码本超过64时继续走原来的串行路径，不能将该内存收益照搬过去。实现见 [训练执行器](../../vexdb_duckdb/include/vex_pq_training_executor.hpp) 与 [训练接入](../../vexdb_duckdb/index/graph_index.cpp)。

### 2. 查询提速：沿图访问部分PQ编码，再用原向量精排

旧PQ路径先遍历所有编码，保留前160个候选，再读取原向量选出前10个。新可选路径先准备一次查询距离表，沿已有图的邻居连接寻找候选；访问节点时读取该节点的PQ编码、查表估距。仍保留160条候选并用原向量精排，最终返回10条。

| 路径 | 找候选时做什么 | 最后如何排结果 |
| --- | --- | --- |
| 原始向量图 | 沿图访问节点，按原向量计算距离 | 使用原向量距离 |
| 原PQ全扫 | 为全部编码估距 | 可选原向量精排 |
| 新PQ图导航 | 沿同一张图，只为访问到的编码估距 | 本次测试精排160条原向量 |

因此，相对PQ全扫，减少了估距数量；相对原始向量图，导航阶段改用PQ编码估距。100K文本ef256档实际约4,147次编码估距，并非只访问256个节点；ef控制内部搜索宽度。该档平均召回99.45%、64连接吞吐提高约69%–76%，不是所有质量档都提速。它复用已有图和PQ训练结果，未重新设计量化公式。实现见 [图搜索距离适配](../../vexdb_duckdb/include/vex_pq_graph_search.hpp) 与 [SearchPQ](../../vexdb_duckdb/index/graph_index.cpp)。

### 3. 提高召回：扩大搜索范围，精排数量不变

PQ估距存在误差，较窄的图搜索可能过早放弃包含真近邻的方向。高召回试验固定ef1536，让查询保留和探索更多可能方向，精排仍为160条。这是现有查询参数的高预算档，不是新量化算法，也没有重建图或改变码本。

该档在两个新1024条代理查询组达到99.960938% / 99.951172%，每次平均需要约1.79万次编码估距。更多搜索增加工作量；最终强对照没有通过稳定速度门槛。低预算与高预算测试的查询组不同，不能将99.45%→99.95%当作同查询受控前后提升。

### 4. 并发缓存：只构建一次，查询复用，写入后失效

精排需要按行号找到原向量，PQ图导航还需要按图节点找到对应编码。将这些位置关系保存在查找表中，避免每次查询重新遍历建立。首次建立时单独加锁，保证多个查询不会一起改同一张表；查询在索引读锁保护下复用稳定内容，写入、替换或重开后使表失效，再按需重建。构建失败时保留待重建状态，防止后续读者看到半成品。额外编码位置表约每节点8字节，首次构建也有成本。实现见 [精排行号表](../../vexdb_duckdb/include/vex_pq_refine_lookup.hpp)、[编码位置表](../../vexdb_duckdb/include/vex_pq_node_codes.hpp)。这项主要验证了正确性和并发行为，没有单独测出其QPS贡献。

### 5. 保存恢复：补存重复向量对应的所有行号

同一个图节点可能代表数据库里的多条相同向量。旧保存格式的节点头只有一个行号，重开后缺少其余关系；覆盖校验发现不完整就退回全表扫描。现在为重复节点补存全部行号，恢复时按记录重建关系，让测试索引在重开后继续可用。它解决的是重开后的性能退化，不是提高每次距离计算的速度；已经由旧版本遗漏的关系仍需要重建索引。实现见 [重复行号保存与恢复](../../vexdb_duckdb/index/graph_index_disk.cpp)。

以上训练、PQ图导航、缓存和保存恢复改动仍在当前源码。最后试验的邻居补查、反向连接补查和长度修正未取得足够收益，已归档撤回，没有混入保留的产品路径。本次说明只核对现有代码与结果，没有启动新测试或修改算法。

## Hardcode与不同业务的适配边界

核对范围为DuckDB的PQ训练、查询导航、参数入口和SQL过滤路径。没有发现按SIFT/DBpedia名称、固定查询ID或预先保存答案做特殊返回的分支；这不是对仓库所有文件的完整审计。此前审查发现了全局跳过重复中心检查和固定候选经验值，本次已按用户要求修复，历史源码及审查记录保留。

实验与审查脚本另有固定数据规模、种子、候选参数、质量门槛，以及针对这次磁盘中断的979条完整计数断言；这些用于固定实验和拒绝不符合记录的输入，不在扩展的产品查询路径中。产品不从实验真值或保存的返回ID读取答案。固定实验设置与运行时可配置能力需要分别判断。

| 项目 | 代码现状 | 对业务适配的含义 |
| --- | --- | --- |
| 向量维度与训练数据 | 维度从FLOAT[N]列类型读取；码本从输入向量训练。pq_m可指定，也可按维度选择一个能整除的段数 | 不限1536维或10万条；更换数据要按新数据建库，效果仍需验证 |
| 查询搜索宽度 | vexdb_ef_search可配置，范围1–65535，默认40；内部还保证搜索宽度覆盖需返回的候选 | 1536是本次固定试验档，不是写死的业务规则，也不会自动为业务选最佳值 |
| 原向量精排量 | 无过滤索引请求按k×vexdb_pq_refine_k_factor计算，并受可用编码数量限制；倍数可配1–1000，默认1关闭精排 | 无过滤的top10、倍数16才对应160条；过滤查询保留原向量精确排序，不再扩大ANN内部k |
| PQ编码和训练调度 | DuckDB当前固定每段8位，即256个代表值；训练任务数超过64保留串行路径。自动选pq_m也使用固定的每段维数偏好 | 属于实现策略，未按业务名称分支；暂未开放任意PQ码长，也不保证所有维度都获得相同训练内存收益 |
| SQL过滤候选量 | 已删除4k及按选择率扩大后再过滤的改写；有过滤时保留DuckDB自然的先过滤、再精确排序 | 不再因全局候选不足漏掉业务子集；弱过滤的速度代价需要报告，尚未实现过滤感知ANN |

重复中心检查：已删除DuckDB的无条件`skip_check_duplicate=true`，改为每段检查实际不同子向量数量。不同值少于码本中心数时允许重复；输入足够多样却中心意外重复则拒绝。样本和中心的NaN/Inf、中心数量仍检查，PG原有显式策略兼容不变。常量、稀疏、重复、正负零、异常塌缩及真实聚类单测通过，ASan/UBSan通过；新SQL回归确认常量和部分子空间常量可建库。不是根据样本总行数或数据集名字放行。

适用范围：线程控制、查找表并发和行号恢复修复不依赖业务内容；无过滤PQ图查询要求保留原向量，只允许L2或余弦，明确拒绝compact与内积。GRAPH_INDEX仅开放单个向量列，多列混合索引暂禁用。过滤查询先筛出合法子集再精确排序，不承诺所有过滤强度都比ANN更快。

目前是可配置、需按业务校准的实现，尚未具备自动选择参数或保证任意业务99.9%召回及速度的能力。实测现已覆盖图像SIFT、文本DBpedia与明确标注的模拟商品/租户过滤；真实商品、业务文档、持续更新或分布变化仍需独立验收，不能沿用已有收益百分比。换embedding模型后也应按新向量重建和验证，不能把旧码本当作普遍适用的模型。

## 实际复现与修复结果

测试使用 4,096 条 16 维合成向量，随后追加 128 条新向量、8 条重复向量，再删除 `id % 13 = 0` 的记录。删除包含重复节点的首条记录，保留共享同一向量的另一条记录。

| 状态 | 表中有效行数 | 恢复后的索引有效行号数 | 重开后的查询 |
| --- | ---: | ---: | --- |
| 未补存重复行号 | 3,907 | 3,899 | 校验发现缺项，保留精确全表扫描 |
| 补存重复行号后 | 3,907 | 3,907 | 实际走索引，结果通过核对 |

旧行为有全表扫描兜底，因此这次复现没有出现表数据丢失。问题是索引覆盖不完整以及检索可能变慢。不能用退回全表扫描后的正确结果冒充索引恢复成功。

固定大小的节点头仍只存一个行号。新增可选字段 `duplicate_row_ids_v1`，只保存有多个行号的节点；字段中包含节点号、行号数量及完整列表。恢复时检查长度、节点范围、重复节点号和行号范围。删除标记继续由原有 `deleted_rids_` 过滤；列表保留已删首条记录，防止再次保存时漏掉仍存活的重复记录。

这个例子有 8 个重复节点，该字段有效载荷为 264 字节，另有 DuckDB 元数据及存储页开销。普通单行节点没有增加逐节点字段。

没有新增字段的文件仍按原节点头路径加载，回归也覆盖了这种布局。已经由旧版本写出、且缺少重复行号的索引需要从表数据重建，加载新代码不会凭空补回缺失关系。未完成旧二进制回读新增字段文件的跨版本验收。

| 原生并发组件 | 16 个首次读者只构建一次；8,000 次读与 100 次失效操作通过 | 使用生产查找表类，外层读写锁保护其使用寿命 |
| ThreadSanitizer | 上述组件检查通过，无报告的数据竞争 | 没有对整个 DuckDB 引擎进行线程插桩 |
| 静态检查 | shell 语法、`git diff --check` 通过 | 未跑三引擎全量 spec、Linux/x86、完整发版构建或真实业务负载 |

实际扩展共完成 **640 次并发 SQL 查询**，另有顺序对照、计划检查和重复记录专项查询。这是正确性回归，不是性能基准。没有把这些查询次数换算成 QPS。

## 接下来提高产品的顺序

### 1. 先弄清实际查询花在哪里

原有 `pq_only` 会扫描全部 PQ 编码，然后可选地取前 `k × factor` 个结果读原向量精排。新加的 `pq_graph` 使用 PQ 距离沿图找候选，见末节。`off` 走原向量图搜索；`compact` 释放原向量，其新增数据也未完整连入图，当前仍扫描全部编码。

因此，换一个距离估计公式，即使单次估距略有改善，也没有解决 PQ 路径随库大小增加的扫描工作。README 已更正“PQ 一定最快”“图先找 4k 个候选”“整体内存缩小 32 倍”和百亿规模的无验证表述。

首轮已通过产品 SQL 比较原向量图、PQ 扫描、PQ + 倍数 4/16 精排和 compact，完成 SIFT 10K/100K、1536 维文本 10K。首轮文本100K中断保留；最新独立补测完成100K文本共享PQ索引上的原图、PQ图和全扫，重开后用独立查询进程测试到64连接，见末节。独立无PQ索引的驻留内存对照仍需补齐；后续继续固定输入并记录：

- `Recall@10`、P50/P95 延迟、单连接与 8 连接吞吐；
- 实际扫描编码数、原向量精排数及查询准备时间；
- 进程内存、索引文件、原向量、图、码本、行号和精排查找表的开销。

`vexdb_index_info().memory_bytes` 当前只汇总部分 allocator，不能当成完整进程内存。原向量存储和精排读取也必须计费。

### 2. 根据测量减少扫描，再选择量化方式

如果瓶颈是扫描全部编码，优先评估“图找候选 + 量化估距 + 少量精排”，或明确的分桶扫描。它需要独立查询模式和质量回归，不能直接改变现有 `pq_only` 的含义，也不能把已经释放原向量的 compact 图当成可用导航。

如果瓶颈是精排读取，再评估减少精排次数、批量读取或缓存布局。每种改动都要在相同召回下比较延迟。

过夜实验中的 SQ8 可作简单对照，RaBitQ 与减中心 RSLM 可作低字节候选；Faiss/参考图成绩仍不足以证明接入 VexDB 会更快。先跑同一条产品查询路径，再决定保留哪一个。

### 3. 下一轮产品门槛

目标：在两组数据各达到至少 95% `Recall@10` 后，与原向量图比较，完整常驻内存减少至少 30%，P95 延迟增加不超过 10%；构建、更新和重开回归均通过。本次查询优化仍保留原向量，没有达到这个完整内存目标，也没有启动新的过夜队列。

若只在较低召回下变快，或计入原向量后不再省内存，就不作为默认模式上线。现有两组各 256 条过夜保留查询仍未使用，不拿它们继续挑参数。

本轮没有提交、推送或发版。过夜实验的冻结源码、失败记录和原结论未修改。相关结果见 [过夜研究报告](../reports/2026-10-26_quantization-overnight-results.md)；历史恢复问题见 [5 月分析及本次补充](2026-05-06_vexdb-duck-restart-deserialize-gap.md)。

## 继续减少 PQ 全量扫描

用户明确要求在召回不明显下降的条件下减少 PQ 扫描。本轮增加独立的 `pq_graph` 选项：查询先计算 PQ 距离表，再使用现有图的邻居连接导航；只对访问到的节点读取 PQ 编码，保留前 `k × factor` 个候选，最后复用原向量精排。`pq_only` 继续表示扫描全部编码，默认仍为 `off`。

这采用已有的图导航与量化估距组合路线。Faiss 官方的 [IndexHNSWPQ](https://github.com/facebookresearch/faiss/blob/v1.15.1/faiss/IndexHNSW.cpp) 也将 HNSW 和 PQ 距离存储组合；本轮直接复用 VexDB 已按原向量建好的图，没有照搬 Faiss 内核，也没有宣称新算法。搜索宽度越大，通常访问越多编码、召回越高，但近似检索无法对任意新查询保证固定召回。

新增节点到编码位置的运行时缓存，64 位平台为每个节点约 8 字节，另外保留原有精排行号表。首次构建和后续并发读取按索引锁保护；写入及替换索引时失效。该路径保留原向量；compact 的新增数据未完整连入图，所以明确拒绝 `pq_graph`。内积的 PQ 导航语义也未验收，明确拒绝。

前置回归发现两项恢复边界：删除节点重开后没有 tids，但仍用于导航，因此通过保存的节点头行号定位其原 PQ 编码；初始批量建图中的重复向量会留下预留空节点，旧保存逻辑把容量当成有效节点数，导致重开时增加无效行号并退回全表扫描。后者通过保存实际已分配节点数修正，旧受影响测试文件保留并重新建索引，不关闭覆盖校验。普通恢复还必须读取保存的 `m`、`ef_construction` 和距离类型；新保存的距离类型采用实际值。

实际性能验收使用新建后重开的同一份索引，对比原向量图、PQ 全扫和 PQ 图导航。两组数据各自已用于开发的 200 条查询，前 100 条用于选参数，后 100 条用于冻结后的检查；它们都不是独立新查询。两组各 256 条过夜保留查询继续不使用。候选网格在计时前登记为 `ef ∈ {64,128,256,512}`、精排倍数 `{4,16}`；只能按前半查询选一个共同参数，然后冻结。

当前门槛针对减少查询工作量：两组主数据上至少 95% Recall@10，相比相同精排倍数的全扫最多减少 0.2 个百分点，平均编码估距次数不超过全扫一半，P95 至少减少 10%。通过后按冻结参数检查后半开发查询，并交换方法执行顺序复测；失败、重建和缺项均保留。这不是此前完整内存目标的替代，也不能把只减少编码估距直接当作 SQL 提速。

原筛选按拟合集的速度选择 `ef=128、factor=4`，冻结后在后半查询上，文本为 99.6%，相对全扫 100% 少 0.4 个百分点，**主筛选未通过**。在打开后半查询结果前，另用拟合集登记了较高召回的独立诊断：先最大化两组最低召回，再看平均召回和速度，选择 `ef=256、factor=16`。登记文件 `quality-selection.json` 明确保留原筛选及失败结论，不将诊断写成原方案通过。

较高召回档在后半开发查询上，100K SIFT、10K 文本均为 99.9%，同倍精排全扫均为 100%；两个顺序相反的独立进程轮次、1/8 连接均通过两组主数据的工作量和延迟门槛。SIFT 10K 的 8 连接 P95 反而比全扫慢，完整尺度检查仍失败。正式对照独立复核 39,600 组真实 SQL top-10，并对照独立原生调用的估距次数与返回 ID；原生计数不进入 SQL 计时。

新实现的 `pq_graph` 和原 `pq_only` 各通过 640 次并发 SQL 回归，覆盖初始批量重复向量、DML、删除首条后的重复向量、连续两次重开；另外检查 cosine 及非默认 `m/ef_construction` 恢复。运行时缓存通过原生并发和 ThreadSanitizer 检查，未插桩整个宿主。结果与可复现入口见 [产品基准报告](../reports/2026-10-27_product-quantization-benchmark.md)。

证据单独存于 `build/product-tests/pq-graph-20261027-v3`。`pq-graph-20261027` 保留首版删除节点恢复失败的二进制、构建记录和日志；`pq-graph-20261027-v2` 保留旧 SIFT 文件重开后未走索引的失败、冻结源码和原协议。重建后的三组索引，其码本、编码、行号顺序和覆盖校验的 12 项保存内容哈希均与此前构建一致。未改训练算法、未使用过夜保留查询，未提交或发布。
