### 原先选中的较快档确实失败了

原协议只按前半查询，在 `ef={64,128,256,512}`、`factor={4,16}` 中选一个共同参数。门槛为两组主数据均至少 95% 召回、相对同倍精排全扫最多少 0.2 个百分点、平均估距不超过一半、P95 至少少 10%。按速度选出的 `ef=128、factor=4` 在拟合集通过，但冻结后：

- SIFT 100K：全扫与图导航均为 99.0%；
- 文本 10K：全扫 100%，图导航 99.6%，下降 **0.4 个百分点**；
- 因此**原主筛选失败**，不把更快的低质量点写成验收成功。

在打开后半查询前，已另行登记较高召回诊断：从原拟合集通过门槛的候选中，先最大化两组最低召回，再看平均召回及速度。该规则选出 `ef=256、factor=16`，冻结在 `quality-selection.json` 后才计算后半查询。它是单独的预登记诊断，使用相同开发检查集；不改原协议、原选择或原失败结论，也不算第二套独立新查询。独立审查结果是：原选择主数据不通过，较高召回诊断主数据通过，两者的小库 8 连接速度均不通过。

## 实现、恢复修复与验证边界

`pq_graph` 复用 `GraphIndexAlgorithm` 的搜索流程，DuckDB 只提供一个读图视图：邻居仍来自已有图，距离改读 PQ 编码，分组四条计算；候选仍交给现有原向量精排。没有改共享图算法或训练数学。参考路线见 Faiss 官方的 [IndexHNSWPQ](https://github.com/facebookresearch/faiss/blob/v1.15.1/faiss/IndexHNSW.cpp)，本轮不是新量化算法的创新证明。

节点到编码位置表在第一次使用时构建，外层索引读锁保护整个使用期，单独互斥锁保护多个首次读者。构建、DML、清空与重开后失效。新增原生并发缓存检查通过：16 个读者、16,000 次读与 100 次写入失效，以及构建失败后重试；ThreadSanitizer 无报告的数据竞争。没有给整个 DuckDB 插桩。

实际扩展的 `pq_graph` 和原 `pq_only` 各通过 640 次并发 SQL 回归，共 1,280 次，另有顺序对照与参数检查。覆盖初始批量重复向量、插入、删除、删除首条后的存活重复行、连续两次重开；检查实际索引计划和返回 ID 对应的真实距离。cosine 及非默认 `m=8、ef_construction=90` 在重开后保留。compact、内积、非 PQ 索引和无效配置会明确报错；默认 `off` 保留。cosine 只有小规模正确性回归，性能表使用 L2。

前置失败均保留：

1. `pq-graph-20261027`：首版重开后，删除节点没有 tids，无法定位其 PQ 编码。后续通过保存的节点头行号查找原编码，删除行仍排除在结果外。
2. `pq-graph-20261027-v2`：原 SIFT 100K 测试文件重开后显示 100,136 个行号，而表只有 100,000 行，覆盖检查让查询退回全表扫描，基准因实际计划未走索引而停止。原因是初始建图预留空节点被当成已分配节点保存；真实使用 99,864 个节点，旧代码保存了容量 100,000。
3. 新保存改为实际分配的 base/upper 数及相应指针范围；重开还读取已保存的 `m/ef_construction/metric`，保存距离类型使用实际值。受影响旧文件没有覆盖或猜测修复，新建文件重开后为 99,864 节点、100,000 有效行号，实际走 `VEXDB_INDEX_SCAN`。旧受影响索引需要从表重建。

三组正式测试索引重新构建在 `pq-graph-20261027-v3/fixtures/`。从保存数据只读导出的码本、完整 PQ 编码、行号顺序和覆盖校验，合计 **12 项 SHA256 与此前构建一致**，保证没有靠换训练模型改善结果；同一新建索引在全部搜索模式间共享图和数据。只有一个图构建种子，不能把重复调用或两个查询进程说成多个建图种子。

正式对照独立核验 **39,600 组真实 SQL top-10**：拟合集 10,800，原选择后半查询 14,400，较高召回诊断 14,400。原生 SQL 计时沿用之前的 prepared statement 方法，包含执行、物化和取返回 ID。计数在单独的非计时原生 API 调用中获取，并核对其返回 ID 集合与 SQL 相同；未把 Python 回放或原生计数耗时当作 QPS。`first_ms` 是已加载索引后该观测点的首调用，不是冷磁盘启动；后续观测点可能已共享缓存。例如较高召回档第一轮首个调用约为 SIFT 100K 2.41 ms、文本 2.96 ms，包含惰性查找表成本，不能只看热查询延迟。

两组各 256 条过夜保留查询仍未使用。本节主表是两组各自已使用的开发查询按前后 100 条划分，文本仍是代理查询，SIFT 上游完整校验值仍未独立确认。文本 100K 的查询和高并发缺项已由前述独立实验补齐；多种子、Linux/x86、三引擎全量 spec、真实客户负载和独立无 PQ 索引的完整内存对照仍缺少。当前范围是 macOS ARM64、DuckDB v1.5.2 SDK 的独立扩展编译与运行。

### 使用与复核入口

已建好保留原向量的 PQ 索引后，可显式选择：

```sql
SET vexdb_pq_search_mode='pq_graph';
SET vexdb_ef_search=256;
```

## 先前的训练资源改动

已让 DuckDB 的 PQ 训练遵守 `parallel_workers` / `threads` 上限。此前 128 维 SIFT 默认产生 32 个子码本，训练同时启动 32 个线程，即使 `CREATE INDEX ... WITH (threads=1)`。每个 K-means 任务都有独立的 `样本数 × 256` float 下界数组；100K 样本时仅这部分同时占用约 3.05 GiB。

训练改动分批启动任务，同批最多使用指定数量的 worker。每个子任务仍使用新线程，保留旧路径的线程内随机数初始状态；直接换成复用线程的池会推进随机数状态，改变码本。大于 64 个子码本的串行路径，以及 `VEX_PQ_TRAIN_SERIAL=1` 调试路径保持原逻辑。上述训练线程改动没有调整 PQ 的训练距离、编码、查询打分或索引文件布局；本次查询及恢复改动已单独列于前文。

## 同一配置的前后对照

使用默认 PQ 子码本数、L2、图参数 `m=16, ef_construction=100, threads=1`。每个版本、每个规模分别启动新进程构建一次。时间是本机单次构建观察，不能代表普遍速度变化。

| SIFT 规模 | 改动前全进程峰值 | 改动后全进程峰值 | 减少 | 构建耗时前 → 后 | 实际结果核对 |
| --- | ---: | ---: | ---: | --- | --- |
| 10K | 442.0 MiB | 131.2 MiB | 70.3% | 3.59 → 3.96 秒 | 3,600 组 top-10 的 ID 及顺序完全一致 |
| 100K | 3.54 GiB | 0.53 GiB | 84.9% | 57.90 → 62.70 秒 | 3,600 组 top-10 的 ID 及顺序完全一致 |

峰值由 `getrusage` 记录，覆盖输入加载、建索引及随后的 SQL 查询全过程；不是只截取构建内部某一段，也不是索引独占内存。100K 构建约慢 8.3%，换取该配置下明显更低的峰值内存。默认线程数受 DuckDB 设置影响，不能把这个百分比套用于所有机器和参数。

两组各检查 3 个精排倍数（1/4/16）、1/8 连接、200 条开发查询、三遍调用，共 **7,200 组实际返回列表**。同规模的整库文件大小、PQ 编码字节和码本字节也相同。

此外用只读连接、不加载扩展，从实际数据库的未绑定索引元数据导出码本、完整编码、行号顺序和向量覆盖校验数据；两种规模各 4 项，改动前后 SHA256 全部一致。这是实际保存内容的核对，强于文件大小一致；没有将有限数据上的一致扩展成所有可能输入的证明。

新扩展还通过 640 次并发 SQL 回归，包括首次精排、插入删除、重复向量及连续两次重开。训练执行器的原生测试和 ThreadSanitizer 检查通过，覆盖 worker 上限 1/2/4、每个子任务的随机数初态、嵌套任务不再开线程、大 M 串行、异常时等待当前 worker 退出。没有给整个 DuckDB 引擎做线程插桩。

## 产品查询基准发现

原基准完成 9 组索引构建、42 个观测点，独立从 CSV 中的真实返回 ID 重算 **25,200 组 top-10**，核对召回、P50/P95 和吞吐算术。覆盖 SIFT 10K/100K 和文本 10K；不是 Faiss 图回放或离线距离缓存的计时。

下表是**改动前产品基线**的单连接 P95。每行都列出实际召回，避免把不同质量的快点直接当成胜出。

| 数据 | 原图 ef=40：召回 / P95 | PQ 无精排：召回 / P95 | PQ ×4 精排：召回 / P95 | compact：召回 / P95 |
| --- | --- | --- | --- | --- |
| SIFT 10K | 99.55% / 0.322 ms | 82.20% / 0.456 ms | 99.95% / 0.543 ms | 82.20% / 1.109 ms |
| SIFT 100K | 97.10% / 0.439 ms | 75.10% / 1.550 ms | 99.20% / 1.857 ms | 75.10% / 1.730 ms |
| 文本 10K、1536 维 | 97.85% / 2.499 ms | 87.90% / 5.675 ms | 100.00% / 5.084 ms | 87.90% / 4.899 ms |

这些原图点都超过原定 95% 门槛；PQ 在这张固定参数网格中需要精排才能超过门槛。各列的实际召回仍不同，不是严格等召回的速度排名。更高召回档位也有不同结果：文本 10K 的原图 ef=512 达到本批查询 100% 召回、P95 为 7.375 ms，PQ ×4 同为 100%、P95 为 5.084 ms。因此不能笼统说 PQ 在所有质量档位都更慢。

训练上限修复后，100K SIFT 的 PQ ×4 仍为 99.20% 召回，单连接 P95 为 1.483 ms。原图 ef=128 在基线中为 99.85%、0.724 ms，当前 PQ 路径在这组数据上仍没有胜出。顺序测试、机器负载和缓存状态会影响延迟；本轮没有把前后约 20% 的延迟差异认定为可重复的提速结论。

原基线中 PQ 的驻留内存还受到训练后 malloc 保留的影响。例如 100K compact 的峰值仍约 3.37 GiB，但查询阶段驻留约 540 MiB。不能把训练进程的一次 RSS 读数直接当成编码表示的必然开销，也不能用它代替“保存后重开、独立查询进程”的比较。本轮资源修复优先解决的就是这个真实构建过程的高峰值问题。

## 如何测量

- 数据复用已准备的 100K 图像库和文本库，以及各自**已经用于开发的 200 条查询**；10K 使用相同库的前缀。没有使用两组各 256 条过夜保留查询。
- 真值来自此前已核验的 float64 穷尽距离：对当前前缀按距离、行号选 top-10。缓存只生成真值，没有进入 ANN 计时。SIFT 上游完整校验值仍未独立确认；文本是归一化 embedding 的分离库行代理查询，不能代表真实用户。
- 全部通过产品 `SELECT id ... ORDER BY l2_distance(vec, ?::FLOAT[D]) LIMIT 10`。检查带参数的真实 `EXPLAIN` 包含 `VEXDB_INDEX_SCAN`。文本使用已归一化输入上的 L2，没有把它说成完成了产品 cosine 路径验收。
- 使用 prepared statement；外部 `Value` 数组构造和 `Prepare` 在每次调用计时外，参数绑定、执行、物化和返回 ID 提取在计时内。它是这个原生 SQL API 入口的吞吐，不含 Python、网络或真实应用客户端开销。
- 每点 200 条查询、三遍、固定随机遍历顺序。8 连接分担同一组查询，报告聚合吞吐与每请求延迟。原始返回 ID、逐调用耗时和墙钟均保留；三遍调用不是三个独立建图种子。
- 每种索引在独立进程构建，再继续查询，包含表、原向量、图、模型、宿主和 allocator 保留内存。数据库文件大小含原始表；索引 allocator 统计不当作全进程内存。图构建只有一个 worker，旧 PQ 的额外并行会单独启动更多线程，修复针对这一点。
- 实验使用固定官方头文件，独立编译、链接并加载产品扩展；没有完成常规全量构建、Linux/x86、三引擎全量 spec 或用户业务验收。

## 中断与缺项

原基准给定 45 分钟窗口，未延长。恢复时确认协调进程和工作进程均已结束；100K 文本原图任务只有加载后的元数据，没有构建完成或查询结果，标为 `interrupted_preserved`。不能仅凭经过的墙钟推断它发生了超时。100K 文本 PQ 和 compact 未启动。已完成 9 组保留，缺少的 3 组不记为成功。

原协议、失败/中断日志、原始扩展和结果没有覆盖。先从源码核对冻结哈希、归档基线源码，再做独立目录中的线程上限修改与前后对照；新的测试不是逾期恢复原队列。复核工具现在能按归档源码的原始哈希审查历史结果，不需要把工作区退回旧版本。

## 下一步

1. 100K 文本的有界构建、保存重开后的独立查询进程及高并发已完成。仍需独立无 PQ 索引和统一驻留条件的内存对照；当前没有达到“两组数据均 95% 召回、常驻内存至少少 30%、P95 最多增加 10%”的完整目标。
2. `pq_graph` 已减少访问编码的范围，100K 文本的接近99.4%召回档已有本地高并发速度收益；下一步补新业务查询、多种子和实际到达负载验证。99.9%档优先研究候选补充或受控回退，单独登记并计入额外成本。小库访问很少编码却未加快，仍需分解图导航、查找、SQL 准备和原向量读取。compact 需要单独解决新增数据的图连接后再评估。
3. 另有一项需单独核验的训练问题：当前 DuckDB 回调返回平方 L2，而 Elkan 的上下界更新依赖满足三角不等式的距离。论文和官方实现都使用相应距离界；应先对照完整 Lloyd 分配建立回归，再决定改动。为保持这次资源改动的结果可比，本轮没有混入训练数学的调整。[Elkan 原论文](https://cdn.aaai.org/ICML/2003/ICML03-022.pdf)、[scikit-learn 官方实现](https://github.com/scikit-learn/scikit-learn/blob/main/sklearn/cluster/_k_means_elkan.pyx)。
