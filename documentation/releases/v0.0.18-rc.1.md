# VexDB-Lite v0.0.18-rc.1

This prerelease contains the tested vector-search improvements and correctness
fixes for PostgreSQL, DuckDB and SQLite. Existing graph and quantized search
remain available; search defaults are preserved.

## Changes

- Restore the mainline RaBitQ support and PostgreSQL extension upgrade paths.
- Correct transaction snapshot handling, PQ training sample selection and
  write-related invalidation so searches use the appropriate visible data.
- Reduce unnecessary PQ scanning, distance calculations and result fetching;
  add optional candidate rescue, reverse traversal and filtered search paths.
  These are general options, without dataset-specific routing.
- Bound DuckDB vector result buffers, avoid carrying unused embeddings through
  output operators, and drain all result batches for large LIMIT/OFFSET queries.
- Fix PostgreSQL builds and SQLite bounded graph construction and Linux
  packaging; preserve SQLite's VexFS and command-line functionality.
- Repair CI paths, archive workflows for removed source trees, and add native
  regression checks for parameters, transactions, filtering and result fetching.

## Verified workload

The final normal-load acceptance used DuckDB v1.5.2 on Linux x86_64 with a
2-CPU, 6-GiB container and a 3-GB DuckDB memory limit. It covered 20,000 simulated
64-dimensional catalog vectors and 100,000 public 1536-dimensional text vectors,
with simulated metadata and result bodies. Raw and PQ configurations were tested
separately with no filter, broad, tenant and price predicates.

All 16 normal-load cases passed their registered goals: 100 catalog requests/s
with P95 <= 50 ms and P99 <= 100 ms; 10 text requests/s with P95 <= 200 ms and
P99 <= 500 ms. The worst observed per-window P95/P99 were 9.822/11.140 ms for
catalog and 99.714/110.303 ms for text. Timings include waiting from intended
arrival through reading complete IDs and bodies, excluding embedding generation,
network RPC and model responses.

Independent review checked 208,896 actual result lists across normal and stress
windows. The minimum recall per 256-query round was 2559/2560 (99.9609375%);
there were no SQL errors, invalid IDs, duplicate results or body-size errors.
All eight stress cases recovered their normal-load goals after stress ended.
The fixed pool contains 512 distinct proxy queries with repeated execution;
these counts are not independent customer questions or a second blind holdout.

## Known limits

- This is a release candidate. The normal-load results above cover the stated
  read-only warm DuckDB workload and explicit search settings. They are not
  guarantees for every dataset, default setting, engine, metric or load shape.
  PostgreSQL and SQLite were not rerun under these normal arrival-rate goals.
- At 64 actual SQL sessions sharing 2 CPUs, text tenant-filtered raw search still
  showed P95 variation between 1.56 and 4.20 seconds. Stress quality and recovery
  passed; uniformly stable stress tail latency is not claimed.
- Four earlier conservative version-speed comparisons remain unsuccessful.
  Their records were retained. Normal-load acceptance does not reclassify them
  as passed, and this release does not claim an overall speedup percentage
  against v0.0.17.
- PQ does not outperform the raw graph in every workload. Tenant-filtered plans
  may choose native exact TopN fetching; that path is not PQ algorithm speedup.
  Full vectors, index metadata and result bodies remain part of storage costs.
- The final 99.9% quality evidence concerns the registered L2/Top-10 cases.
  It does not establish the same quality for all metrics or parameter choices.

## Packages

Linux x86_64 and AArch64 packages are validated for PostgreSQL 16–19,
DuckDB v1.5.2 and SQLite, with separate debug symbols and a SQLite/VexFS
command-line package. DuckDB extensions must match the host DuckDB version.
Use SHA256SUMS.txt to verify downloads and select the matching architecture.

Final package verification results and source provenance accompany the release.
